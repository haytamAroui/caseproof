# ADR 0029 — Browser intake through existing signed dossier services

Status: implementation proposal for owner-requested F3, 2 November 2026. No production or new schema approval.

The loopback composition exposes `/v2/workspace/intake` projections over the installed development organization-discovery, matter-creation, bundle-registration, private source and dossier RPCs. The browser never talks directly to Supabase. Existing signed JWT membership, matter grants and Storage RLS remain authoritative; no new grant, actor, organization metadata authority or service-key path is introduced.

The installed registration accepts exactly four originals: DOCX draft, UTF-8 text inventory, two PDF exhibits (text or scanned). Limits are 5 MiB per original, 12 MB decoded bundle, 64 pages per PDF and 17 MB HTTP body. New intake mutations have a bounded 180-second browser deadline. Expensive parse/format preflight checks every original before registration or object writes. Registration is atomic metadata; distributed object writes are explicitly not atomic. Reservation precedes transfer and acknowledges identities only, never preservation. Upload completion requires fresh signed readback of each original and a final current context check. Unknown outcomes remain unresolved.

Bundle registration derives a domain-scoped UUIDv5 from the canonical case and complete ordered metadata. Reselecting exact originals after a cold restart replays the same installed operation; changed bytes cannot overwrite it. A create-operation UUID may appear as opaque `operation` query state so an interrupted create can replay after reauthentication without persisting a title, organization choice, credential or file. The caller must restore identical form values; database idempotency rejects conflicts. Confirmation still uses the existing canonical dossier endpoint, binds the bundle signature and is freshly read back before showing saved. PDF, printed and bundle page spaces remain separate; all bindings require explicit human input.

Storage preservation, parser coverage, inventory completeness and verification are distinct. Image-only pages remain partial without OCR; this flow does not claim a completed OCR job. Existing page-worker execution remains a separately configured backend capability. No source deletion or operator cleanup is exposed to the browser. Stopping transfer aborts the client request and warns that remote work may have committed. Protected acceptance must own synthetic matter and object cleanup before writes.

Rollback removes the new router include and React routes/contracts. Existing sources, grants, snapshots, legacy clients and confirmations remain intact. No SQL/migration, new provider, production mount or deployment is included. C01/C05/C06/C07/C08/C09/C11/C12/C14/C16/C17/C20/C21/C24/C25 apply. Genuine browser, adversarial recovery and independent review evidence is recorded separately in the F3 acceptance record.

Recovery reads an already registered original before attempting another write. Supabase standard upload may return HTTP 400 for an existing object, while older adapter tests used HTTP 409. Neither status proves success. After a denied/uncertain/racing write, only fresh signed exact-byte readback may reconcile; a missing, revoked or corrupt read fails. Existing lower-level denial classification and no-overwrite policy remain unchanged. Reference: https://supabase.com/docs/guides/storage/uploads/standard-uploads .
