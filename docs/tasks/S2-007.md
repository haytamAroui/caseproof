# S2-007 — Signed Auth to disposable tenant-RLS bridge (bounded proof)

**Status:** Stage 2 development-only test slice, proposed for security review. No production database driver, role, route, migration, tenant provisioning or customer-facing endpoint.

**Product:** ExceptionDesk finance first, with sector-neutral CaseProof kernel. **Parent:** docs/ROADMAP.md Stage 2; S2-001/002/003/005/006 and proposed ADR 0010 (PR #27). **GitHub:** this slice can be reviewed independently of unmerged S2-004 prototype PR #28.

## Why this slice exists

The CaseProof development Supabase PostgreSQL 17 instance already has the seven-table caseproof schema and RLS, but on 2026-10-22 still has **zero real Auth users**, organizations, memberships and cases. Simulated JWT claims in S2-002 and fake verifier tests do not demonstrate that a genuine Supabase-issued bearer token is checked before a database access. An unwired/deny-all adapter also cannot prove functional tenancy.

**S2-007 currently proves only two separate things, in one optionally credentialed workflow:**

1. Real Supabase Auth password sign-in for two separate **preexisting, email-confirmed development users**; remote /auth/v1/user verification and tampered-signature rejection, reusing S2-006 code.
2. **Separate, disposable PostgreSQL service**: map the verified identities to random per-run HMAC-pseudonymous test UUIDs, seed two synthetic organizations/cases/document versions and test actual role/RLS predicates using **simulated, transaction-scoped SQL Auth claims**.

This is stronger integration coverage than isolated stubs but **does not prove production Supabase PostgreSQL connectivity, live Auth->PostgREST JWT binding, safe persistent connection pooling or actual tenant provisioning**. No signed token reaches Postgres; SQL claim binding here is explicitly an *authorized test simulation*. It is not a supported method for authenticating an untrusted DB client.

## Files

- scripts/verify_s2_007_disposable_tenancy.py: guarded runner; source identities appear in memory only and are turned into per-run pseudonyms; refuse any non-local PostgreSQL target; no bearer/credentials/UUIDs printed.
- tests/test_s2_007_disposable_tenancy.py: negative input cases and protection checks for opt-in, GitHub environment, branch and ephemeral database.
- .github/workflows/s2-007-signed-tenancy.yml: manual-only workflow_dispatch on trusted protected main; existing caseproof-dev-live-auth environment only; disposable postgres:17 service.
- .github/workflows/kernel-boundary.yml: automated synthetic A/B PostgreSQL tests (no Auth secrets; cannot claim genuine user verification).

No SQL migration or remote Supabase project/table/role change. The S2-002 migration content remains identical to the existing reviewed proposal.

## Manual prerequisites and operational guardrails

1. Use Supabase Auth management UI to create and confirm two distinct development-only accounts in caseproof-dev: https://supabase.com/dashboard/project/ldwmocpxwskvhoojndrd/auth/users . Never use raw INSERT into auth.users. No accounts existed at the verified inventory time. Do not use real customer, family, or production identities.
2. Use GitHub environment caseproof-dev-live-auth with **only main** deployable, independent environment approval where available and protected main branch. **Never** put credentialed values in repo/organization secrets or files. Configure the five existing S2-006 environment secrets: CASEPROOF_DEV_PUBLISHABLE_KEY, CASEPROOF_DEV_AUTH_A_EMAIL, CASEPROOF_DEV_AUTH_A_PASSWORD, CASEPROOF_DEV_AUTH_B_EMAIL, CASEPROOF_DEV_AUTH_B_PASSWORD. Use only sb_publishable_, no sb_secret_/service_role.
3. After this PR is reviewed and merged to main, manually dispatch "S2-007 Signed Auth and disposable RLS (manual only)" from main. The runner has a PostgreSQL 17 service on localhost and a short-lived test-only postgres password. Do not connect to the remote caseproof-dev database. The script requires both CASEPROOF_S2_007_REAL_AUTH=YES and CASEPROOF_LIVE_AUTH_TEST=YES and refuses to run without the existing S2-002 strict local disposable flag.
4. **Only the final step receives environment secrets**. The job checks out reviewed main with persist-credentials false, installs a PostgreSQL client, and runs the standard-library Python harness without third-party dependencies. Do not loosen the environment branch policy, add pull_request triggers or print SQL/server error text.
5. Successful manual marker: S2-007_SIGNED_AUTH_WITH_DISPOSABLE_RLS_POSITIVE_NEGATIVE_REVOCATION_PASSED. This is **not** production release approval, an IdP sign-out test or true live tenant isolation.

## Adversarial verification

| Probe | Required outcome |
|---|---|
| Two distinct valid real signed credentials, remote /user verification | Both verified; tampered JWT rejected; same subject identities forbidden |
| Pseudonym mapping | Distinct, fresh randomized fixture UUIDs per run; actual Auth UUIDs and tokens absent from PostgreSQL and logs |
| Positive control for each synthetic mapped user | A sees A's case/document version, B sees B's; deny-all policies fail |
| Cross-tenant A/B reciprocal checks | Neither sees foreign case/doc/version; IDs are never used as SQL authority outside test |
| Empty/no claim | Zero case/source metadata visible |
| One transaction's LOCAL claim followed by ROLLBACK and a new transaction | No old subject leaks to next transaction (test-only, not production pool proof) |
| Membership revoke for A | A cannot see its earlier own case or version; B retains own access |
| Non-local database / wrong user/database / no opt-in | Hard failure **before** remote Auth requests or any SQL |
| No manual environment secrets in normal CI | No real Auth requests; clearly labelled synthetic PASS only |

## Remaining S2-007 / production release blockers

- Two actual Supabase Auth accounts and the protected environment must be configured by an authorized operator; **not completed by this PR**.
- Run and retain the genuine Auth+disposable-RLS workflow evidence.
- Review, implement and prove an actual least-privilege **application runtime PostgreSQL connection model**, with independent authenticated-user identity propagation, tenant-owned positive and negative reads, 404/503 masking and per-request authorization. A direct privileged role plus untrusted SET claim is prohibited.
- Test actual IdP session revocation independently of membership deactivation, with an explicit acceptable token staleness model and positive controls for authorized subjects.
- Test live role connection-pool cleanup, cross-org member changes, sign-out, deletion/ban and concurrency. No real tenant DML or live API is authorized until these gates, persistent evidence, source storage and S2-004 authorized transaction model pass.
