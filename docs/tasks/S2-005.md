# S2-005 — Tenant-isolated read-only CaseAccessRepository adapter

**Status:** Stage 2 executable integration slice, separate from migration
deployment. **Dependency:** S2-002A migration PR #23, which is not installed
on Supabase until an independent security approval clears the release gate.

## Purpose

The S2-001 authorization service requires one joined lookup of a case and the
**current** membership for a cryptographically verified subject. This
implementation adds a PostgreSQL DB-API-compatible adapter for that port:
`apps/api/postgres_case_repository.py`.

### The exact query

```sql
select c.id, c.org_id, c.case_revision, c.created_by_user,
       m.user_id, m.org_id, m.active, m.actions
from caseproof.cases as c
inner join caseproof.organization_members as m
    on m.org_id = c.org_id
   and m.user_id = %s
   and m.active = true
where c.id = %s
limit 2
```

The subjects and case IDs are required canonical UUIDs passed **only as SQL
bound parameters**. There is no separate case-existence query, tenant header,
role argument, client-supplied org ID, JWT user metadata, permission bypass,
SECURITY DEFINER function or writable route.

The result is mapped to strict `StoredCase` and `StoredMembership`
values, and checked again to ensure the case ID, subject ID and
organization agreement. Corrupted rows, unexpected permission values,
duplicates, SQL errors, connection failures and ambiguous joins fail with
the same sanitized `AccessStoreUnavailable` exception; the application
translates it to 503. A normal foreign/unknown case yields `None` and
the application masks it as 404. Runtime authorization checks active
membership and requested action on **each** request.

### Trust and DB connectivity requirements

`PostgresCaseAccessRepository` takes a server-owned `connection_factory`.
No connection string, environment variable, Supabase key or default
privileged role is embedded in this module. No actual database connection
is configured in the application. The future production composition root
must supply a **reviewed least-privilege connection** whose authentication,
pooling, transaction boundaries, tenant permission and TLS requirements
are validated separately.

The simple reader protocol is compatible with a DB-API cursor that returns
positional records (e.g. psycopg cursor), but **psycopg is not added to this
PR** and no live PostgreSQL connection or SQL adapter integration is
claimed. The existing S2-002 disposable PostgreSQL security CI checks
the concrete underlying schema/RLS rules. This PR tests the parameterized
single-query boundary with clearly labelled in-process cursor test doubles;
no direct SQL/DB integration or real JWT has occurred in this slice.

Even with an authorized `AuthorizedCase`, the adapter's result is
point-in-time authorization only. **Do not reuse it across a write
transaction** to authorize promotion or audit decisions. S2-004 must
atomically reload latest active membership, snapshot/policy/version,
perform the revision-protected state update, insert append-only audit and
finalize the idempotency result in one transaction or fail closed.
No `/v2` route is enabled.

### Acceptance tests

`tests/test_s2_005_postgres_case_repository.py` exercises:

- A verified subject with a current active organization membership;
- Foreign/missing case returns the same `None` with one SQL query;
- Invalid UUIDs, SQL injection-shaped case IDs and unexpected data never
  alter SQL or open the connection;
- Cross-tenant case, membership and subject mismatches, duplicate rows,
  malformed permissions and unexpected revision fail closed;
- Database outage for foreign and unknown cases maps identically to 503;
- Connection cleanup and sanitization of underlying database errors;
- Existing S2-001 `CaseAccessService` permission checks with adapter output.

The cloud CI additionally checks the adapter with strict mypy along with
all existing kernel/SQL/architecture tests. Any future live SQL driver
and secrets provisioning requires its own reviewed, locked dependency
and integration suite.
