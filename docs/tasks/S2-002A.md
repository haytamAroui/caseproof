# S2-002A — Canonical migration and dev deployment gate

**Status:** Development-only schema applied on 2026-10-22; S2-002B reconciles the repository migration filename to the exact remote history. No production use authorized.

## Migration requirements

1. Generate a versioned SQL file using the installed official Supabase CLI
   (`supabase migration new caseproof_tenant_foundation`). Do not guess
   timestamps or rename version files arbitrarily.
2. Copy the reviewed `db/proposals/S2-002_tenant_foundation.sql` SQL exactly
   into the CLI-generated migration, keeping its SHA-256 consistent with the
   reviewed proposal. The canonical file becomes the source for subsequent
   deployments; the proposal remains a historical review artifact.
3. Test the canonical file against **real PostgreSQL 17** in isolated CI:
   constraints, RLS, authenticated read vs write restrictions, cross-tenant
   FK denial, membership revocation, genuine two-connection compare-and-swap
   and audit-persistence failure rollback. Do not equate simulated
   `auth.uid()` with genuine signed Supabase Auth.
4. Inspect schema, grants and security advisors in the target development
   project, confirm empty migration history and absence of unexpected
   application tables. Preserve strict schema-only and least-privilege
   isolation. Do not introduce a `SECURITY DEFINER` shortcut.
5. **Before applying** to the remote project, obtain a recorded human
   approval for the exact versioned SQL and deployment target. Retain
   migration and recovery sign-off, and verify applied version, RLS and
   no inadvertent public access afterward. An agent-run CI test alone
   is not that approval.

## Independent security finding and fix

The first independent Codex review of PR #23 identified that
`caseproof.audit_events.actor_user_id` originally pointed directly to
`auth.users` without guaranteeing that a named human belonged to the
**same organization** as the case. The canonical versioned migration and
its reviewed proposal now enforce a **composite
`(org_id, actor_user_id)` foreign key** to
`organization_members(org_id, user_id)`. The actor-type check also
requires service events to carry no human actor ID.

The negative SQL fixture now attempts to attribute tenant B's user to
tenant A's audit event and attempts a service event carrying a human
actor; both must fail. Correctly scoped human and service events must
succeed. This revised schema was run with `BEGIN` / `ROLLBACK` against
real CaseProof dev PostgreSQL and independently checked to leave
zero schemas, tables and synthetic user records. GitHub cloud CI
runs the canonical file against ephemeral PostgreSQL 17, including
tenant RLS, two-session concurrency and failed-audit rollback.

**Important:** A database composite FK establishes actor membership
record existence, not current active human authorization at decision
time. The eventual S2-004 transaction must additionally verify
current active membership, required action permission, separation of
duties and timestamped attestation.

The migration's original verified fingerprint changed after this
security fix. The new canonical/proposal SHA-256 is
`02782c14182f7e53b0c967e404e9413cd0fb083ec3958d56d514987e1187ecd4`
(proven by CI). The subsequent development installation is documented below.

## Limitations

No production database, signed-session JWT, private document bucket, live
`/v2` endpoint, authorized human approval, or atomic audit writer is
implemented merely by installing this schema. S2-003's Auth adapter
remains unconnected until user/session and RLS integration tests exist.
S2-004 must implement durable atomic state+audit+idempotency.

## Applied dev migration record (2026-10-22)

The repository owner explicitly instructed proceeding with the next
**development-only** rollout. After the reviewed SQL and tests passed,
CaseProof's canonical schema was installed into the dedicated Supabase
`caseproof-dev` project via the connected Supabase migration service.
The server assigned migration version **`20261022001009`** and name
`caseproof_tenant_foundation`, which differs from the original offline
CLI-generated candidate filename (`20261021232955`). To prevent a second
schema application on future `supabase db push`, the repository filename
was aligned to the **actual remote version** in the follow-up S2-002B PR.
The SQL bytes and SHA-256 remain identical to the independently reviewed
proposal; only migration metadata and references changed.

Post-deployment catalog inspection found seven zero-row application tables,
all RLS-enabled, five authenticated SELECT policies, zero anonymous read
permissions, and no authenticated INSERT/UPDATE/DELETE privileges. Audit
and idempotency have no client SELECT/WRITE grants. The security advisor
returned two **informational** `rls_enabled_no_policy` notices for the
intentionally private audit/idempotency tables. A rollback-only RLS/tenant
role fixture passed against the **installed schema**; a separate query
confirmed no synthetic test users, organization rows, case rows or audit
rows remained.

**Important remaining limitation:** tests used simulated PostgreSQL
`authenticated` role and `auth.uid()` settings, not real signed Supabase
Auth sessions. No PostgreSQL driver, customer records, human reviewer
attestation, production credentials, /v2 routes or durable atomic writer
were enabled. A real two-tenant authenticated integration is the next
security gate.
