# S2-002 — Proposed PostgreSQL tenant persistence and RLS: reviewed SQL + rollback tests

**Status:** SQL proposal + executed, rollback-only database verification. **NOT a
registered Supabase CLI migration or an applied/persistent application schema.**
**Stack:** On S2-001 PR #20 (which is stacked on KRN-109 PR #19).
**Target:** `caseproof-dev` Supabase project in EU Central
(project reference `ldwmocpxwskvhoojndrd`), currently empty.

## Implemented in this PR

- `db/proposals/S2-002_tenant_foundation.sql` — private `caseproof` schema
  with **seven** tenant-aware tables:
  `organizations`, `organization_members`, `cases`, `documents`,
  `document_versions`, `audit_events`, `idempotency_records`.
- `db/proposals/S2-002_rls_rollback_test.sql` — real PostgreSQL negative
  tests, executed **inside one BEGIN / ROLLBACK transaction** only after the
  DDL. Synthetic Supabase `auth.users` identities, two organizations,
  memberships and case/source rows are **not persisted**.
- `tests/test_s2_002_sql_contracts.py` — repository/CI regression guards
  for schema/table coverage, RLS enablement, role grants, tenant composite FKs
  and presence of the real negative SQL test matrix. Static checks complement
  but **do not substitute for** the PostgreSQL role-based tests.

## ERD and trust decisions

```text
auth.users (Supabase-owned)
   └─< caseproof.organization_members (org_id, user_id) >─┐
                                                        │
caseproof.organizations (id) ────────────────────────────┘
   └─< caseproof.cases (org_id, id; created_by_user)
        ├─< caseproof.documents (org_id, case_id, id)
        │    └─< caseproof.document_versions (org_id, document_id,
        │                                      version_number, sha256)
        ├─< caseproof.audit_events (org_id, case_id, actor, input_digest)
        └─< caseproof.idempotency_records (org_id, case_id, operation, key)
```

- **RLS strategy:** The private `caseproof` PostgreSQL schema is **not
  exposed as a Supabase Data API schema**. All seven tables have
  `ENABLE ROW LEVEL SECURITY` and deny-by-default ACLs. The authenticated
  database role gets `USAGE` on the schema and **SELECT only** on five
  non-audit tables; no INSERT/UPDATE/DELETE/DDL or audit/idempotency grants.
  `anon` receives no schema usage. Never expose the private schema without
  a new reviewed API/grants threat assessment.
- **Authorization source:** Supabase `auth.uid()` from a verified session
  and the database's **current, active** `organization_members` rows.
  No `user_metadata`, `app_metadata` role assumption, HTTP `X-Tenant`,
  custom user-set GUC as authority or client-submitted owner ID. Members
  can SELECT their own active membership only. `case:read` grants org/case
  metadata; `evidence:read` separately grants document/version metadata.
  No policy recursively reads the membership table via its own policy.
- **Ownership constraints:** `cases` has globally unique ID and
  `UNIQUE (org_id,id)`; tenant-owned children use composite
  `(org_id,case_id)` or `(org_id,document_id)` foreign keys.
  The creator must have an organization membership at insert time.
  The input source hash is a 64-character lowercase SHA-256 string, **not
  provenance authenticity**. No original file is stored in a public table.
- **Permission source:** Membership `actions` is a server-maintained,
  typed constrained array. Production membership creation, revocation and
  grants **must go through a trusted server workflow**; client writes are
  deliberately not enabled. A separate admin membership-management use
  case, invitation flow and immutable membership-change audit remain.
- **Audit/idempotency:** Schemas contain immutable-reference metadata and
  a unique operation/key constraint. They have no exposed client grants.
  **Do not accept production decisions or approvals yet**: Stage S2-004
  must establish the server-side least-privileged writer, append-only
  enforcement, idempotent result replay and single transaction for state +
  audit + idempotency. No API or worker uses the tables in S2-002.
- **No SECURITY DEFINER functions, custom bypass function, public JWT
  claim setter or service role access was introduced.** The security
  boundary in S2-001 remains a separate authorization service.

## Database validation — executed on 2026-10-21

The connected Supabase `caseproof-dev` PostgreSQL project reported
**ACTIVE_HEALTHY** and `17.11.0.003` before the exercise, with zero
application tables. The following *single-call*, transaction-wrapped
sequence was executed against its actual PostgreSQL engine via the
Supabase connector:

```sql
BEGIN;
-- contents of db/proposals/S2-002_tenant_foundation.sql
-- contents of db/proposals/S2-002_rls_rollback_test.sql
ROLLBACK;
```

The test returned the exact marker
`S2-002_ROLLBACK_ONLY_RLS_TEST_PASSED`. Real PostgreSQL assertions
passed for tenant A vs B visibility, case-only users unable to read
document metadata, revoked membership, unauthenticated `auth.uid()`
access denied, denied client writes/audit reads, seven enabled RLS
tables, and composite-FK rejection of a forged cross-tenant relation.

A **separate subsequent query** independently returned:
`caseproof_schemas_left=0`, `app_tables_left=0`, and
`synthetic_auth_users_left=0`. The test did not create permanent
schemas, users, data or storage objects.

**Critical test limitation:** `set local role authenticated` and
`set_config('request.jwt.claim.sub', ...)` simulate PostgreSQL runtime
claim context, and can be spoofed by a privileged SQL client. This tests
RLS policies under that identity, **not cryptographic token verification**
or the Supabase Data API's actual JWT boundary. S2-003 must test
real signed tokens, claim/audience validation, revocation and key rotation.
No genuine untrusted HTTP user, remote JWT, authenticated browser,
production connection pool or application has accessed these tables.

## Indexes and performance plan

Membership PK `(org_id,user_id)`; active membership index
`(user_id,org_id)` for `auth.uid()` lookups; tenant-scoped case, document,
version and audit ordered paths. Use explicit projections and keyset
pagination for audit. Validate plans with `EXPLAIN (ANALYZE,BUFFERS)`
on representative, sanitized tenant sizes before launch. No broad JSONB,
unbounded scan permission or arbitrary owner bypass. The indexes above
are initial access-path hypotheses, not measured production claims.

## Migration and recovery gate — NOT yet performed

1. **Independent human/security review** of the exact proposal, RLS
   strategy, private schema visibility, future least-privilege writer and
   Supabase Auth identity/session assumptions under Constitution C11/C13.
2. Once approved, use the **Supabase CLI** to create a canonical, versioned
   migration filename (`supabase migration new ...`), copy the reviewed
   SQL into it, pin tool versions, and commit it with verification evidence.
   Do **not** treat the `db/proposals` file as an applied migration.
3. Apply only to `caseproof-dev`; verify catalog/grants/RLS with real
   `authenticated` and `anon` privileges, then test real Supabase
   Auth-issued JWT users including tenant B, revocation, concurrency,
   unsupported operations, cross-tenant joins and worker context.
4. Recheck advisors/security. Run database migration repair/recovery on
   a fresh disposable clone; for additive tables, restore from backup
   only after policy review, avoid destructive data/history drops.
5. No production rollout, customer uploads or business decisions until
   verified identity, storage isolation and atomic state+audit passes.
   The existing `v1` dev header-based API is **not** production safe.
