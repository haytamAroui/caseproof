# S2-006 — Genuine signed Supabase Auth session probe (development only)

**Status:** Executable, manual-only integration probe. Does **NOT** register
a v2 route, create an Auth user, provision a tenant, connect to Postgres,
or grant review/approval permission.

**Dependencies:** S2-003 server-side Supabase Auth verifier merged in
`main`; S2-005 read-only case repository PR #24 (this PR is stacked
on #24). The S2-002 development schema is **already installed** under
recorded migration `20261022001009` in `caseproof-dev`.

## Why this slice exists

The earlier S2-003 tests used unsigned synthetic JWTs and transport fakes.
They are useful for failure-path validation, but cannot establish that
the actual configured Supabase Auth service issued a signed user session
or rejects a modified signature. At the time of authoring, the dedicated
`caseproof-dev` Auth user table contains **zero** real accounts, so a
genuine live test cannot be reported as passed.

This task provides a reproducible, opt-in, secret-safe live check.

`SupabasePasswordSignin` in
`apps/api/supabase_password_signin.py` calls **only** the fixed
`https://ldwmocpxwskvhoojndrd.supabase.co/auth/v1/token?grant_type=password`
endpoint over system-verified TLS, with a publishable key and credentials
held only in memory. It follows no redirects and validates the bounded,
typed session response. It deliberately never exposes the refresh token
or logs Auth payloads.

`run_live_auth_probe` in `apps/api/live_auth_probe.py`
authenticates two **distinct, pre-existing, confirmed** dev accounts,
runs both returned access tokens through the **real project-pinned
`SupabaseAuthUserVerifier`** (which calls `/auth/v1/user` on the
Supabase Auth server), checks matching subject and issuer, and mutates
a significant byte of JWT A's signature to confirm the Auth service
rejects the altered token. A normal password login still has
`human_authenticated=False`; login is not evidence of legal review.

### API key privilege boundary

Both the server-side `HttpsSupabaseUserLookup` and the development
`SupabasePasswordSignin` require the modern **`sb_publishable_`** key
format, with a nonempty bounded alphanumeric/base64url-like suffix.
Legacy JWT-form API keys, `sb_secret_` keys, `service_role` keys, malformed
values and HTTP-header injection characters are rejected **at object
construction**, before any network request. This intentionally excludes
legacy anonymous JWT API keys to avoid accidentally accepting a forged or
privileged JWT-form key. Configure only the explicit **publishable** key
from `caseproof-dev`; never paste service-role secrets into GitHub.

The CLI script `scripts/verify_s2_006_live_auth.py` never prints tokens,
emails, passwords, subject UUIDs, refresh tokens, or server errors.
It emits only the success marker
`S2-006_REAL_SIGNED_AUTH_SESSIONS_AND_TAMPER_REJECTION_PASSED`
or a sanitized failure class name. Explicit opt-in
`CASEPROOF_LIVE_AUTH_TEST=YES` is required. The GitHub Action
`.github/workflows/s2-006-live-auth-sessions.yml` is
**workflow_dispatch only**, never scheduled or run on pull requests.

## Setup — two real dev accounts are a prerequisite

The Supabase integration currently exposes project/DB/SQL operations
but **no account-provisioning action**. Don't create fake records in
`auth.users` by manual SQL; that bypasses real GoTrue account/session
semantics. Use the real Supabase Auth UI or reviewed administration API
to create two separate test accounts; verify emails, and keep passwords
outside the repository and assistant conversation.

### Restrict the credentialed GitHub Action to trusted revisions

**Do not place these credentials in repository-level or organization-level
Actions secrets.** A `workflow_dispatch` can select a branch, so an
unreviewed branch could read such broadly scoped secrets. If credentials
were previously configured there, remove/rotate them before enabling
the live workflow.

An admin must first configure GitHub Settings → Environments →
`caseproof-dev-live-auth`. Under **Deployment branches and tags** choose
**Selected branches and tags**, and allow **only `main`** (not "no
restriction" and not "protected branches only" without verifying branch
protections). Where practical, require an independent reviewer for
environment deployments and disable administrator bypass. Ensure `main`
is protected against unreviewed writes. **No live probe should be
dispatched until these environment settings are verified.**

Set these five names as **environment-only secrets** for that environment:

- `CASEPROOF_DEV_PUBLISHABLE_KEY` (publishable key for this dev project)
- `CASEPROOF_DEV_AUTH_A_EMAIL`
- `CASEPROOF_DEV_AUTH_A_PASSWORD`
- `CASEPROOF_DEV_AUTH_B_EMAIL`
- `CASEPROOF_DEV_AUTH_B_PASSWORD`

The workflow also checks for the exact repository and `refs/heads/main`,
checks out `main` explicitly, and invokes `python3 -m
scripts.verify_s2_006_live_auth` with the trusted runner's Python
(3.11+) and **no setup-uv or dependency installation**. All three
source modules required by the probe are standard-library-only; the
five secrets are bound only to the final probe step. The `.yml` file
uses JSON syntax, which is a YAML-compatible serialization, so the
regression test can parse and assert the actual workflow structure with
Python's standard-library `json` module, without fragile text matching
or adding dependencies.

Only after environment protection, account creation and secret setup:
choose GitHub Actions → **S2-006 Real Supabase Auth sessions (manual only)**
→ Run workflow and select `main`. No privileged/service-role key,
database password, production data or production-connected environment
is required. Create only test accounts; do not reuse personal/customer
credentials.

## Verified by standard PR CI versus not yet verified

**Automated normal CI:** Tests cover HTTPS project pinning, bounded payload,
Auth response failures, two identity separation, signing-tail tamper
rejection, wrong issuer/verified ID, no login-to-human privilege shortcut,
opt-in requirement, and secret-safe failure output. All of these use
clearly labelled *fake* transport/verifier doubles. The existing
S2-002 PostgreSQL test separately verifies tenant RLS using **simulated**
SQL auth claims.

**Not yet exercised:** Real Supabase Auth password sign-in and actual
JWT validation, because **there are no provisioned test accounts and no
GitHub secrets in this workflow yet**. A green PR CI must not be described
as successful signed-session verification. The manual workflow result is
the first permitted real JWT evidence. A subsequent task must create
two tenant organizations/memberships with a trusted provisioning flow,
supply a reviewed server-side least-privilege database connection,
and run actual multi-tenant reads and revocation tests. No `/v2`
route should be enabled until that evidence exists.

**Further security gates:** Sign-out and revocation semantics, MFA/human
attestation, membership grants, tenant removal, private evidence storage,
atomic state+audit/idempotency (S2-004), real connection pooling/session
isolation, and failure injection. No user metadata can authorize a role.
Never commit real credentials or JWTs to tests, README, CI logs or issues.
