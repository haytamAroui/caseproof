# S2-008a3 — Read-only exact evidence join and typed reconstruction

**Status:** Proposal + CI prototype, disposable DB only. Not a production DB adapter, Auth-bound query, canonical migration, deployed service or reviewer/approval API.

## Outcome

Read back an exact KRN-102 evidence locator by joining the S2-008a immutable evidence graph in **real disposable PostgreSQL 17**, then decode it through the S2-008a2 typed persistence contract. Independent **client** connections must reconstruct the *same versioned citation metadata* rather than trust a stale in-process object. **The PostgreSQL server itself is not restarted in this test**; server-restart and crash-recovery verification remain unimplemented.

## Implementation

- `apps/api/postgres_evidence_reader.py` owns one parameterized, read-only SQL query against the *proposed* S2-008a schema. It joins anchor → representation → layout → opaque document/version mapping → original version/document with tenant, case, original and representation SHA concordance. The query requires **both** a server-chosen expected scope (`org_id`, `case_id`) and an independently verified `ExpectedEvidenceParent` (exact opaque document/version/representation IDs plus hashes).
- `get_exact_anchor_metadata()` passes only named bind parameters to a supplied dictionary-row cursor. Missing/foreign/stale identity is masked as a not-found result. Unknown columns/schema version, malformed JSONB, unexpected layout kind/coordinate convention or scoped-ID mismatch fail closed. It returns `UnverifiedEvidenceMetadata` with `eligibility_established=False`. **Do not construct ExpectedEvidenceParent from the untrusted anchor row.**
- `scripts/verify_s2_008a3_reader.py` executes the **same SQL text** through a fresh disposable `psql` process, using a strictly allowlisted **synthetic fixture-only** substitution shim (not production SQL binding). Two separate client connections reconstruct the same typed anchor (no PostgreSQL server restart); same-org foreign case, stale original SHA, changed representation ID and stale version yield no row. No real tenants, bytes or Auth identities.
- `tests/test_s2_008a3_readonly_reader.py` verifies the fake dictionary-row boundary refuses foreign/corrupt projections, wrong basis/layout, duplicate JSON keys, a missing trusted parent, invalid key or unexpected column. CI runs this after S2-002/S2-007/S2-004/S2-008a on ephemeral Postgres and type-checks the adapter.

## Trust/limitations

This is a **metadata** read in a superuser-owned disposable CI fixture. It proves neither production least-privilege database access nor genuine JWT/session security (S2-007 remains incomplete). It does not authenticate source bytes/object availability (S2-009), verify source authenticity, independently attest parser layout correctness, authorize an evidence claim, resolve contradictory facts, nor unlock `review_ready`/`approved_conclusion` (S2-004 production writer). There is no runtime wiring, current-head publication, new Supabase migration, storage bucket or private data in this PR.

A read-only SQL join does not by itself create a secure authorization boundary. Before integration, the application must resolve the expected parent independently under current verified user/tenant membership and run the query through a least-privilege, identity-scoped connection, with positive/negative real Auth/RLS cases and session revocation proof. Any direct use of caller-supplied context with a privileged connection is prohibited.
