# S2-003 — Supabase Auth server-verification adapter (NOT LIVE)

**Stage:** Stage 2 identity integration slice for review.  
**Base:** S2-001 PR #20, with its corrected joined authorization lookup.  
**Independently pending:** S2-002 RLS/schema proposal PR #21. No database migration applied.

## What this adds

`apps/api/supabase_auth_verifier.py` implements the `BearerIdentityVerifier`
port in S2-001, using the *Supabase Auth server's own* bearer verification
endpoint `GET https://<exact-project-ref>.supabase.co/auth/v1/user`.
`HttpsSupabaseUserLookup` enforces a fixed, validated 20-character project
reference, HTTPS, certificate validation through the system TLS stack,
single request path, no HTTP redirect following, a bounded response, timeout
and a **publishable key only**. It does not accept arbitrary URLs, service-role
keys, user-controlled tenant IDs or roles.

The `SupabaseAuthUserVerifier` parses JWT header/claims locally **only as
untrusted envelope data**. It rejects malformed/big JWTs, `alg=none`, unknown
algorithm, unexpected project issuer, audience or role, invalid UUID subject
or session, expired/future-issued JWTs. **This parsing does not verify a
signature.** Identity is returned only after a successful request to the
trusted Supabase project's Auth server, and only if the confirmed user ID
matches the signed JWT subject. Deleted, banned or anonymous users fail.
No local key, refresh token, role, model confidence or JWT user metadata
can directly authorize membership or approval.

**Important separation:** A confirmed Supabase Auth user is NOT, just by
logging in, an independently verified human reviewer. The adapter returns
`human_authenticated=False` until a separately reviewed reviewer assurance
process is implemented. This deliberately prevents the current S2-001
`REQUEST_APPROVAL` path; it does not block read access once a real
tenant repository exists.

No `/v2` endpoint is registered, no Auth account is created or verified
in a running application, no CaseProof secret is installed, no persistent
schema is installed, and no production customers or AZComply data are used.

## Testing and honest limitations

`tests/test_s2_003_supabase_auth.py` exercises contract rejection for
wrong issuer, audience, role, bad session/subject, timestamp and malformed
JWTs, mismatched/deleted/banned/anonymous users, Auth 401/403,
service unavailability, 3xx redirect, oversized or malformed JSON, fixed
hostname, timeout, no approval and absence of live API routes.

**Synthetic tests use a clearly labelled fake Auth response** to exercise
codepaths; they do not cryptographically validate JWT signatures and do
not prove HTTPS egress/TLS trust under production networking. Passing this
PR's CI is NOT proof of real Supabase Auth sign-in. The Auth service itself
must verify token signature and user identity; the adapter never uses
unverified JWT fields to bypass this step.

Before deployment, configure the CaseProof dev project's publishable key
through server-side config; issue *real* test user sessions in the dedicated
dev project; check `getUser` success for genuine tokens and rejection of
forged/revoked/expired/other-project tokens; validate stricter session
revocation (short TTL + session lookup where legally required), rate
limits, regional network failure, key rotation and clock skew. Use only
reviewed actual tenant/RLS repository roles. No role/user claims from
user-editable metadata, no live approval until human identity and durable
audit gates pass.
