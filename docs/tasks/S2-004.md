# S2-004 — Atomic state + audit + idempotency (CaseProof-native design)

**Status:** Internal **disposable-only** PostgreSQL 17 atomic observation reference and strict Python fingerprint contract implemented and tested in CI; not a production writer, installed migration, authenticated approval, exposed API or deployed behavior. Latest combined-branch CI remains a separate verification gate.
**Parent:** Stage 2 existing merged S2-001/002/002A/003/005/006 work; see `docs/adr/0010-stage2-native-durability.md`.
**Data boundary:** dedicated `caseproof-dev` project only after separate schema/runtime approval; no AZComply database or code dependency.
**Priority:** P0. **Type:** security-sensitive, bounded internal application/SQL adapter slice.

## User-facing purpose

A reviewer must never see a resolved finance exception when its authorized decision, case state, audit record and retry receipt disagree. Once Stage 3 is ready, this transaction primitive backs a single human-controlled action, such as recording a reviewed resolution. Stage 2 delivers only the **internal mechanism**, with no public write/approval surface.

- `caseproof.audit_events` exists with actor type, case/tenant scope, event schema, correlation and immutable input hash.
- `caseproof.idempotency_records` exists with organization/case/operation/key uniqueness and persisted fingerprint.

- `contracts/v2_operation_matrix.json` uses permissions absent from current `CaseAction` and membership CHECK. Do not equate `conclusion:request_approval` with `conclusion:approve`.

## Application contract to design (internal, never request-body authority)

### Inputs

`DecisionCommand` (suggested versioned value contract, subject to implementation review):
- `operation`: typed supported command kind; first slice must be a non-approval internal operation.
- `case_id`: canonical case UUID (resource lookup, not authorization).
- `expected_case_revision`: positive version read by client; must be rechecked in DB.
- `expected_scope_version`, `expected_manifest_revision`, `expected_policy_version`: frozen preconditions from server-verified case context.
- `idempotency_key`: stable bounded opaque retry key; reject empty/oversize.
- `request_id` / `correlation_id`: operational correlation; distinct from idempotency.
- `payload`: strictly typed and versioned semantic request; never arbitrary user-controlled new state or role.
- **No** `org_id`, `actor_id`, `role`, `human_authenticated`, `approved` or `tenant_id` fields accepted as authority.

`TrustedCommandContext`:
- Created **only** by the server's authenticated application composition root, never from JSON or model output.
- Includes a verified session subject, IdP assurance result, server-selected resource ownership, policy reference and action requested.
- This data remains insufficient for authorization until the transaction reloads current membership/permissions and snapshot.

`DecisionReceipt`:
- Schema version, case ID, committed case revision, action kind, immutable audit event ID and request/correlation IDs, semantic-result fingerprint and recorded result reference.
- No raw source quotes, customer documents, credentials, token payloads or unneeded PII.
- Same key and identical semantic fingerprint returns the stored receipt only when current authorization allows access; changes or expired rights do not leak earlier data.

### Distinguish record types

`recording requested approval` != `giving approval`. `business risk acceptance` != `evidence supported`. `evidence grounded` != `approved conclusion`.

The initial internal command handler cannot manufacture `approved_conclusion`, `BUSINESS_EXCEPTION_ACCEPTED` or an otherwise consequential state from a test-double, a caller-provided boolean or an unsupported coverage result. It must remain behind a production-disabled composition port until the graph/assurance gate is proven.

## Required transaction algorithm

All steps below are one **real PostgreSQL** transaction, under a documented least-privilege runtime identity.

1. **Entry:** validate strict request schema and verify IdP session *outside* transaction. No external provider calls or object uploads under an open DB transaction.
2. **Lookup and lock:** resolve current case + membership in tenant scope, lock the relevant membership row in a mode that prevents concurrent revocation before commit and the case row for revision update. Document and test global lock ordering to prevent deadlocks. A stale pre-request `AuthorizedCase` snapshot alone never authorizes the mutation.
3. **Current permissions:** verify active membership, `case:read`, operation-specific action, separation of duties and—if ever relevant—independently established human-review assurance. Missing/foreign resources map uniformly to masked not found; DB/IdP failure fails closed.
4. **Idempotency:** look up (org, case, operation, key) inside the transaction. Canonicalize/version/hash trusted actor scope, semantic request and preconditions, distinguishing keys, JSON types and algorithm versions. Same key+fingerprint returns committed receipt after current auth; different fingerprint is a conflict. Concurrent same-key inserts must be serialized by the unique constraint and a documented wait/re-read or equivalent retry path.
5. **Fresh authority and serializability:** validate the effective server-selected policy and **exact, frozen** case/evidence/coverage revision set. Stage 1 synthetic `promotion_preflight`, incomplete coverage, untrusted assessor labels, stale anchors or unverified human authority cannot satisfy this. **All writes publishing any current evidence/finding/link/coverage/manifest/policy head must first lock this same case aggregate and advance `case_revision` atomically.** The decision holds the case lock through validation and commit. CAS on `case_revision` is *insufficient* if any current-head writer bypasses that protocol. If a shared aggregate lock cannot be demonstrated, adopt separately reviewed `SERIALIZABLE` transactions with bounded safe retry. Race actual head/policy changes against a decision in PostgreSQL.
6. **CAS:** update precisely one current authorized case revision with `WHERE case_revision = expected` (and trusted tenant/case predicates). Zero affected rows is a conflict, not a silent retry.
7. **Audit and receipt:** insert the append-only audit event and durable idempotency record/receipt; link event and before/after states to the decision/reference. Use typed schema versions, normalized event reason and correlation. Require all referential constraints.
8. **Commit then acknowledge:** return the committed receipt only after confirmed commit. On failed audit insert, missing policy, authorization change, timeouts or other transaction error: roll back all changes; no success marker.
9. **Ambiguous commit:** if transport breaks after commit initiation, reconcile by key and immutable fingerprint under newly checked authorization before repeating any mutation. Never assume no commit occurred.

The exact SQL/writer connection design and migration are **separate security-reviewed choices**. Do not add broadly granted DML, an unscoped privileged function, service-role bypass or `SECURITY DEFINER` without explicit review. A custom `SET app.user` or `SET request.jwt.claim.sub` alone does **not** authenticate the caller.

## Non-approval first slice and dependency ordering

Build and test the transaction primitive in a **disposable PostgreSQL 17 service** from the canonical migration, using synthetic identities clearly labelled as fixtures. A first internal-only event or constrained case transition may exercise the transaction, but MUST fail closed in any public runtime until the required persistent policy/evidence data exists. Do not pretend a fabricated `human_authenticated=true` test object is a real reviewer.

**Independent prerequisites for a real promotion/approval command:**
- S2-007 real Auth -> application -> runtime DB role tests and reviewed active membership provisioning, revocation and human reviewer assurance;
- S2-008 durable immutable finding/link/coverage/policy graph, validated against KRN-101–109;
- S2-009 verified private source storage and parser representation lineage for source-backed claims;
- v2 permission catalog aligned across Python enum, DB membership constraints, operation matrix and reviewer signoff;
- successful S2-004 concurrency, audit rollback, idempotency and crash/unknown-commit tests.

Do not create a live `/v2` write route as part of S2-004.

## Data design and proposed implementation seams

These are **candidate paths, not claims they exist**:
- `apps/api/decision_commands.py`: narrowly typed application command port/use case with no SQL dependency; validates trusted context shape and fail-closed behavior.
- `apps/api/postgres_decision_writer.py`: server-owned DB-API transaction adapter with scoped parameterized SQL, cursor/session cleanup and explicit error normalization. Keep transaction identity handling in the composition root; no global mutable principal.
- `db/proposals/S2-004_*.sql` and new Supabase CLI migration only **if** missing append-only permission/receipt constraints require schema changes, after separate human review and migration-safety approval.
- `tests/test_s2_004_decision_contracts.py`: pure negative/authority tests.
- `scripts/verify_s2_004_database.py` + CI service: real Postgres integration tests with simultaneous independent connections and rollback-only fixtures.

Potential schema refinements to review: event/receipt reference integrity, stable receipt JSON/schema version, optional decision revision table, immutable audit enforcement under the exact runtime role, authorization/grant provenance and policy snapshot keys. Do not mutate `20261022001009_caseproof_tenant_foundation.sql`: migrations are append-only.

## Adversarial acceptance matrix (mandatory)

| Test | Expected result |
|---|---|
| Missing/invalid token and forged principal in request | No DB mutation; 401/422 as appropriate |
| Foreign case, revoked/inactive membership, wrong org | Denied and no case-existence oracle |
| Real membership revocation races concurrent command | Either revocation commits before authorization and command is denied, or command commits while authorization is held; never an unauthorized post-revocation commit |
| Action-only membership lacking `case:read` | Denied consistently with RLS |
| Attempt to approve as creator / unverified human | Denied; ordinary signed user is insufficient |
| Forged `actor_id`, `org_id`, role, policy or `human_authenticated` body | Rejected at boundary |
| Current statement/anchor/coverage/policy changed, including concurrently | All writers share the case lock+revision (or reviewed SERIALIZABLE equivalent); stale/conflict, no successful approval |
| Revoked IdP session independent of membership | Expiry, ban, session revocation or deletion denied on the next command; a cached verified principal never bypasses fresh verification |
| Real tenant positive controls | Verified tenant A and B each access their own fixtures via the runtime/pool before cross-tenant denials are accepted |
| Unsupported quote or contradictory required issue | No unqualified approved state |
| Two simultaneous writers with same expected revision | Exactly one committed transition; other deterministic conflict |
| Concurrent same idempotency key, same fingerprint | Exactly one state+audit event, same authorized receipt |
| Same key, different payload/fingerprint | Conflict; no duplicate event |
| Revoked membership tries to replay old key | No unauthorized receipt disclosure |
| Inject audit insert failure | Case revision/state + decision + receipt all rolled back |
| Inject receipt insert failure | Case revision/state + audit all rolled back |
| Commit-success acknowledgment lost | Reconcile same key before any retry; no duplicate decision |
| Database connection/pool failure | Fail closed, sanitize errors, no leaked connection state |
| Audit/event tampering via runtime account | UPDATE/DELETE denied |

Require real PostgreSQL for concurrency and rollback tests; a fake cursor suite does **not** prove atomic behavior. RLS fixture with simulated `auth.uid()` does not prove actual remote Auth or application principal binding; S2-007 must provide that separate evidence.

## First bounded executable implementation (disposable-only)

The feature branch introduces `apps/api/internal_observation_contract.py`, `db/proposals/S2-004_disposable_observation.sql`, `scripts/verify_s2_004_database.py` and the focused contract tests. CI runs the S2-002 fixture first, then executes the S2-004 disposable PostgreSQL 17 verification in the **same ephemeral service**.

The SQL reference function only appends an internal observation event, increments a candidate case **revision without changing its lifecycle state**, and records an idempotency result. It explicitly revokes execution from anonymous and authenticated roles and is neither a canonical Supabase migration nor registered in the application. Its synthetic actor UUID is **not an authenticated identity**, and its database administrator test role is **not a proven least-privilege production connection**.

Demonstrated only **after** real CI passes: PostgreSQL statement rollback on audit/receipt constraint failure, serializable-per-case membership-lock ordering, stale-revision conflict, concurrent identical-key replay, different-key conflict, revoked membership replay denial and detection of corrupted saved receipt. These are narrower than the full S2-004 release requirements.

No inference should be made about real Supabase sessions, production reviewer permission, durable KRN-101–109 graph, object storage, or valid transition to `evidence_grounded`/`approved_conclusion`. That needs S2-007–009 and an independently reviewed production writer, permission catalog and migration.
