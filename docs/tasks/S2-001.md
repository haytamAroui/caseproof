## Implementation and precise trust boundary

`apps/api/access_control.py` contains a fail-closed authorization use case and
three interface/value contracts:

1. `BearerIdentityVerifier.verify_bearer(token)` must be implemented
   *outside the kernel* by a trusted **server-owned** adapter that
   cryptographically verifies the token and requires the configured issuer,
   audience, algorithm/key identity, UTC expiry, signature and current
   revocation/session validity. The service checks the verified subject
   type, pinned issuer/audience and UTC validity interval again.
   `UnavailableBearerVerifier` is the **only default** and denies all access.
   There is deliberately no DIY JWT parser, insecure X-Tenant authorization,
   user-editable metadata roles or mock provider in non-test runtime code.
2. `CaseAccessRepository` is a **port, not a data store**. A future
   PostgreSQL-backed implementation must read a globally unique case ID's
   server-owned `owner_org_id` and the *current* membership for the verified
   `subject_id` + org. Read each membership afresh per authorization;
   never use editable JWT `user_metadata`, `X-Tenant` or a submitted
   `tenant_id` as permission. Revocations and role changes must affect
   subsequent reads. No fallback to anonymous access when storage is down.
3. `CaseAccessService.authorize` checks identity **before** case lookup,
   requires current active tenant membership and explicitly scoped action
   permission. A missing case or foreign/unknown membership is masked
   identically as HTTP 404; a verified member without the requested
   permission is 403; absent/invalid token is 401; IdP/store outage is 503.
   A reviewer *requesting* approval must be a human from the verifier,
   not the case creator, and explicitly permitted by membership.
   The return `AuthorizedCase` is **only a point-in-time permission check**,
   not an approval, a reusable bearer capability, a state transition or
   a locked database transaction.

The current `tests/test_stage2_case_access.py` uses **clearly named test-only
fake providers and a shared in-memory repository**. It exercises two
organizations and multiple actors in one store. This establishes the
authorization algorithm's denial behavior, **not** that a real token has
been cryptographically verified, Supabase membership is trustworthy,
RLS is configured, or data isolation survives real SQL/worker traffic.

No v2 route can be enabled with a fake or unconfigured adapter, and no
write or consequential action is implemented in this task. The v1 dev
adapter remains unchanged and visibly warns that its tenant header is
caller-controlled; v1 is unsuitable for production.

## Database proposal for separate human approval — NOT IMPLEMENTED

The database standard requires review of the ERD and migration before
creating schemas, repositories, RLS policies, triggers or indexes. The
design below is **review-only**.

```text
auth.users (Supabase-owned user UUID)
  | 1
  | *
organization_members (org_id FK, user_id FK, active, permission set, version)
  | *
  | 1
organizations (org_id PK)
  | 1
  | *
cases (case_id globally unique PK, org_id NOT NULL FK, created_by_user,
       case_revision, current_scope/manifest, policy_version)
  | 1
  | *
case_audit_events (event_id PK, org_id, case_id, actor_type/user_id,
                   state_before/after, input_digest, idempotency_key,
                   event_schema_version, occurred_at)
  | *
idempotency_records (org_id, case_id, operation, idempotency_key,
                     input_digest, response_ref, committed_at)
```

**Tenant relationships:** composite `(org_id, case_id)` key on case-owned
children and composite FKs so cross-tenant references cannot occur. Auth
`user_id` derives only from a verified Supabase identity. Owner membership
creation must be atomic with new organization creation. Case identifiers are
globally unique, not ambiguous reused local strings.

**Authorization/RLS design choice proposed:** direct **user-scoped JWT**
database operations with validated membership policies where possible;
otherwise a reviewed least-privilege dedicated service role executing
transaction-scoped identity from a trusted verifier, never an unguarded
service-role bypass. A custom GUC (`SET app.tenant`) alone cannot prove
authorization. RLS needs actual runtime-role test coverage for direct
lookups, joins, writes, version rows, audit, object-storage references and
workers. Admin/service credentials never leave the server. Explicit
least-privilege grants and policy evaluation are mandatory. The read-only
authorization port here does **not** establish either strategy.

**Uniqueness/checks:** memberships keyed `(org_id,user_id)`, versioned
permission provenance and non-null/active status; case `org_id` not null;
unique `(org_id,case_id)`; revision positive; audit append-only at runtime
role; uniqueness on `(org_id,case_id,operation,idempotency_key)` and
conflict on changed fingerprint. All timestamps timezone-aware UTC;
permissions must be validated typed values, never role labels from token
metadata. Immutable source/version and link history remains kernel-owned.

**Transaction boundary (future S2-002/003):** authenticate and resolve
tenant membership, check latest case/coverage/policy/version snapshots,
take concurrent-write protection, validate human decision scope, update
case state, append immutable audit event and finalize idempotency result
**in one transaction**. If audit insert fails, roll back the case state
and response; repeat same key+fingerprint returns original committed
result; different fingerprint 409. Worker retries and expired membership
need fresh authorization and atomic CAS, not this point-in-time snapshot.

**Indexes and query discipline:** membership `(user_id,org_id)` and
`(org_id,user_id)` PK as needed; case `(org_id,case_id)`; audit
`(org_id,case_id,occurred_at,event_id)`; idempotency unique key. Only
add access-path indexes justified by EXPLAIN plans and actual runtime
permissions; use narrow projections and keyset pagination.

**Migration and recovery plan:** separately reviewed additive migration,
test on disposable PostgreSQL with real RLS runtime roles and Supabase Auth
claims, seeded two-tenant negative suite, backfill/dual-read strategy if
legacy rows exist, transactional migration and recovery rehearsal,
explicit validation of grant/revoke, concurrent retries and audit-insert
fault injection. Rollback must preserve audit and source version history
and avoid destructive drops; schema reversal may require forward-fix,
documented before production. Retention, lawful deletion, tenant offboarding,
backup/restore and private object-storage ACLs must be reviewed before
customer data.

## Remaining Stage 2 gates

- **S2-002:** independently approved PostgreSQL schema/migrations + actual
  tenant membership repository and tested RLS policies.
- **S2-003:** verified Supabase Auth/JWKS provider adapter with trusted
  issuer/audience/algorithm/key selection and rotation/revocation tests;
  actual token issuance from configured test IdP. Never claim token
  authenticity from an in-memory fake.
- **S2-004:** single transaction for state+audit+idempotency and failure
  injection, crash/restart and write-concurrency tests.
- **S2-005:** add the first authenticated read-only v2 HTTP route, only
  after mandatory gates above pass. Preserve existing v1 compatibility;
  disable public v1 before production or require a separate security plan.

No new endpoints, migrations, providers, credentials or paid resources
are created in S2-001. Protected branch, independent review and owner
authorization are still required before merge/deploy. In particular
`CaseAccessService` MUST NOT be wired to the demo test doubles in
production; its trust begins only at a properly verified IdP adapter
and a PostgreSQL repository with independently checked RLS.
