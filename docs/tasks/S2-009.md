# S2-009 — Private Evidence Vault: staged immutable source bytes

**Status (2026-10-22):** S2-009a internal application protocol and simulated failure tests proposed in PR; **NOT** deployed private storage, durable SQL ledger, verified parser output, client upload route, signed-URL service, or release-ready evidence.

**Product fit:** Evidence Kernel source/version identity for finance invoice↔PO exception review first; future CaseProof dispute dossiers reuse the identical source trust model. **Dependency:** ADR 0010, S2-008a–a3, and genuine Auth/tenancy S2-007 (the credentialed Auth/live runtime gate remains incomplete).

## Trusted outcome — not an upload checkbox

A stored document must have a **recorded immutable version, private object identity, exact byte count and SHA-256, read-back verification, independent availability history, and current action-scoped access checks** before anyone can resolve a citation from it. A hash proves the examined bytes match a recorded digest; it does not prove authenticity, legal truth, semantic support, document completeness or authorized review.

### S2-009a — implement a safe coordination protocol (this PR)

- `apps/api/evidence_vault_protocol.py` defines strict `UploadIntent`, `VaultScope`, `VaultRecord`, `VaultState` and separate `PrivateByteStore` and `VaultLedger` ports. All are independent CaseProof code with **no Supabase SDK or AZComply runtime dependency**.
- `begin()` requires a **stable, trusted-entrypoint-generated UUIDv4 intent ID** carried unchanged through retries, then creates a **durable pending upload intent before** any blob dispatch. If a pending insert committed but acknowledgment was lost, `VaultUnknownOutcome.intent_id` lets the caller reconcile by exact scope+intent ID and a same-ID retry returns the original frozen object key after confirming hash/size/type. A different semantic payload under the same ID conflicts. The production handler MUST persist/forward the stable ID before remote dispatch and bind it to authenticated actor and case. Never generate a new request ID on retry. The object key is scoped to tenant+case but ends with a fresh cryptographic random component; neither filename nor digest is used as an authorization grant. **The `VaultScope` type does not authenticate anyone**; caller must obtain tenant/case authority from a trusted current membership and session validation, outside this module.
- `upload()` permits only frozen size/media/hash-compatible bytes, performs immutable `put_once` (never upsert), reads exact bytes back and publishes a verified source only after SHA-256 and count match. `VaultLedger.publish_verified` MUST implement the **same transaction** for source/version record, availability revision, trusted immutable audit event, aggregate revision/invalidation and idempotency receipt. Merely returning a `VaultRecord` in a fake adapter is not proof of this obligation.
- Unknown object-write result or PostgreSQL commit acknowledgment returns `VaultUnknownOutcome`. `reconcile_pending()` inspects durable metadata and the exact immutable object. It **never blindly writes again**; a missing object stays pending, a mismatched object stays unverified, and a previously committed verified intent is not double-published.
- `read()` checks authoritative current in-scope state and exact stored digest at use. A confirmed missing or modified verified blob leads to `mark_unavailable`, which MUST atomically audit and bump the case aggregate/current availability head to invalidate related approval/export snapshots. If the audit/DB action fails or storage cannot be reached, the caller gets **no bytes**. A restored blob cannot silently turn an unavailable source into verified again.
- `tests/test_s2_009a_vault_protocol.py` exercises lost pending-insert acknowledgment and same-ID replay, as well as deterministic fake-ledger transitions and failure injection for post-PUT timeout, post-commit acknowledgment loss, two-tenant denial, checksum/readback drift, missing published bytes, audit-failure rollback, outage vs confirmed missing, stale availability during read, no second upsert and no live API.

The 5 MiB limit and accepted MIME list are **bounded in-memory reference safeguards**, not an approved product limit. A production upload must use streaming with bounded memory, content sniffing/PDF/UBL validation, malware scanning and scanning/quarantine before publication. Never log bytes, filenames, signed URLs, service keys or tokens.

### S2-009b — durable PostgreSQL ledger and private object integration (NOT IMPLEMENTED)

The next required implementation is a **separately reviewed additive** database migration, CLI-created with the installed Supabase CLI, and a private storage adapter behind the `PrivateByteStore` port.

1. Design `vault_intents` and `source_availability_revisions` with composite tenant/case/source FKs and immutable source/representation object-version identities. Pending intent must carry trusted actor/correlation and an **append-only creation audit event**; do not accept unaudited pending rows.
2. Prove actual transaction behavior on real disposable PostgreSQL 17: pending intent+audit commit, verified source publication+audit+case CAS+idempotency in one transaction, confirmed object loss+availability+case head invalidation in another, and rollback on deliberate audit failure. Add concurrent writer/recovery duplicate-key and revocation-race tests.
3. Implement an immutable, private Supabase Storage or equivalent object adapter. **Never upsert** into an existing object key; configure bucket as private and a least-privilege, action-scoped access strategy. Object metadata/content in Storage and relational `caseproof` SQL **are not a common transaction**. Quarantine/pending and orphan reconciliation are mandatory.
4. Give workers an explicit, bounded recovery/retry policy. Staged source bytes can exist before source publication; cleanup **only** after proving no approved source, legal hold, pending replay, current reference or audit retention requires them. Use event/outbox reconciliation to recover when the object upload succeeds but its metadata transaction fails.
5. A signed URL is a **bearer capability**. Supabase signed download URLs remain valid through their configured expiry even after Auth sign-out or JWT key rotation; cache behavior can further complicate revocation. Prefer an authenticated server-mediated download for highest-sensitivity documents or a narrowly time-limited signed URL issued **after** a fresh access check. Do not claim instantaneous revoked-session invalidation for an already-issued URL. Never place signed URLs in audit events or application logs.
6. For post-publication corruption/deletion, deny citation resolution/export and append an **audited** unavailable/corrupt source availability revision under the same case-head lock. Never automatically overwrite/replace bytes at the original key; restored original bytes require fresh checks and policy/coverage reassessment.

### S2-009 release gates

| Threat/failure | Required real proof |
|---|---|
| User A / B; same-org different cases | Signed Auth + actual least-privilege DB and private Storage policy allow own source and deny cross-scope operations |
| Unconfirmed storage PUT | Quarantine remains pending; next recovery discovers object or remains pending; **no blind duplicate PUT** |
| Successful write but SQL transaction fails | Original object remains quarantined/orphaned for reconciliation; no falsely verified source |
| Audit insert fails | DB source/availability/head/idempotency transition fully rolls back |
| Source bytes change after publication | Exact read fails; append audit + unavailable head + case revision bump; export and promotion blocked |
| Object missing vs provider transient outage | Both deny reads; only definitive missing changes persistent availability |
| Stale scope/reviewer/source version | No read, signed URL, export, upload overwrite or approval |
| Crash/worker restart | Prove actual durable persisted retry outcome and no doubled side effects, not merely two fresh DB connections |
| Private content security | Confirm no public bucket URL path, exposure through Data API, leaked logs, excessive signed TTL, or service-role bypass |
| Erasure/retention/legal hold | Tenant ownership, audit retention and lawful deletion order proven under explicit policy |

## Actual status and follow-on

S2-009a **only** verifies a Python protocol with injected memory-only fake storage and state. It does **not** establish durability, real RLS, signed Auth, private object storage or secure deployment. The first actionable next PR is **S2-009b**: disposable PostgreSQL intent/availability transactions, independently reviewed schema migration proposal, then storage adapter and actual Auth checks. No live Storage bucket or remote SQL changes are authorized by this document.
