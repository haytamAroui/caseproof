# KRN-106 — Versioned Issue and Source Coverage Ledger

**Status:** Feature implementation for review; no production deployment.  
**Base:** `main` after KRN-101–105; design input ADR 0009 (*Proposed*).

## Problem

A processed-document flag, a matching quote, or an agent's successful run
cannot establish that an investigation is complete. Every case must declare
required issues and expected source versions, keep unresolved/missing sources
visible, and pin the issue-to-link evidence consulted at one manifest revision.

## Stage 1 implementation

- **Immutable CoverageManifest:** case ID, positive scope version, manifest
  revision, explicit policy version, required issues with acceptance-policy
  identifiers and expected-source associations, expected source inventory,
  link ID/assessment revision/finding revision selectors, required finding
  IDs for each issue, and exclusion proposals. All identifiers are sorted,
  unique and cross-linked. Every relied-on link must belong to an explicitly
  required finding, and all required findings must have their own links.
- **InMemoryCoverageLedger:** tenant-keyed append-only manifest history.
  Identical scope versions cannot silently remove or replace required
  issues, acceptance criteria or source identities; scope changes require a
  new scope version and rationale. Old manifests remain inspectable.
  Neither a rationale nor the in-memory store authenticates a scope editor.
- **Source inventory:** `expected_unknown`, `missing`, `pending`,
  `processed`, `failed`, `excluded`. A processed source needs a
  successful last attempt with representation IDs. The evaluator verifies
  that the source version and all asserted representations are registered
  in the trusted tenant namespace. Attempts are immutable value records,
  **not** proof of an actual parser run or authorization.
- **Issue evaluation:** consults the current KRN-104 link revision, verifies
  its finding revision and that its anchor came from a declared processed
  source/representation, and checks KRN-103 exact content fidelity. Every
  required finding's **complete current link inventory** must be declared;
  new or omitted contradictory/supporting links block coverage, including
  links introduced during evaluation. Exclusions must be immutable tuples. Links
  with contradictions, qualifications, indeterminate semantics, earlier
  unreviewed contradictions, or insufficient/unassessed link-local sufficiency
  do **not** satisfy ordinary completion. A current contradiction remains
  visible even if another link supports the claim. An issue with no relied-on
  link is `open`, not `supported`, regardless of source processing.
- **Completion outcome:** a read-only `CoverageEvaluation` with issue
  dispositions and explicit typed blockers; `ordinary_complete` is true
  only if **no blockers** remain for the *declared frozen scope*. It is
  **not** an approval, legal or factual truth decision or guarantee that
  the declared issue universe is exhaustive.
- **Exclusions:** require an explicit reason, claimed reviewer/permission/
  audit references, but these values are **untrusted input**. Stage 1
  **always blocks ordinary completeness on exclusions**, rather than
  simulating reviewer authorization or claiming that an excluded mandatory
  source is accounted for. A future authorized policy may separately
  produce a qualified result; the original gap must remain visible.
- **Optimistic stale checks:** compares immutable manifest and link revision
  selectors before and after evaluation, rejecting observed changes.
  This is a reference read/read check, not a transaction or durable lock.

## Adversarial acceptance

Tests must cover: known processed+supported source; unknown expected source;
missing/failed/pending source; false processed claim with missing source
bytes or representation; processed source without evidence links; wrong
finding/link revision; stale manifests and policy pins; contradictory,
qualified and inconclusive evidence; historical contradiction followed by
support; exclusions with forged reviewer references; source/issue omission
without a scope bump; explicit scope revisions that retain older history;
cross-tenant isolation; no change to older kernel and v1 public API.

## Security and limits

**No actual user authentication, authorization, separation of duties, RLS,
private storage, durable audit, verified parser execution, transactional
promotion, immutable datastore, paid customer workflow, or export.** Tenant
scope must come from a trusted server. Attempts, semantic assessments,
exclusion reviewer names, claimed audit IDs and effective policy versions
can be forged by an untrusted caller and **must not be accepted as approval**.
This model cannot discover missing sources that were never entered in scope.

Conservative Stage 1 ordinary completion additionally requires every
relied-upon current link to be fidelity-`matched`, `supports`, and
link-locally `sufficient`, and blocks unreconciled historical contradictions.
The later KRN-107/provenance and Stage 2 authorization flows may supersede
these rules with an explicit versioned policy; never silently weaken them.
