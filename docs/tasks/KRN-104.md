# KRN-104 — Immutable finding-to-evidence assessment links

**Status:** Implemented on review branch; CI/review required before merge.
**Parent:** `main` after KRN-101/102/103 integration (PR #13).
**Design:** ADR 0008 and ADR 0009 (both still marked Proposed).

## Problem

A model can accurately quote a source while drawing a false inference, so a case must preserve
the precise finding text/revision, typed source/representation anchor, deterministic citation
resolution and fidelity result, assessor's proposed semantic relation, and link-local sufficiency
independently. Contradicting evidence cannot disappear because another link supports the claim.

## Bounded implementation

- `FindingStatement`: immutable finding ID, consecutive positive integer revision, hidden exact
  statement text and computed SHA-256 of UTF-8 text. An unanchored candidate can be registered
  but gains no review/approval state.
- `SemanticAssessmentProposal`: explicit `supports`, `contradicts`, `qualifies`,
  `inconclusive`, or `not_assessed`, and independently `sufficient`, `insufficient`,
  or `not_assessed`. Typed assessor kind, reference, method version, nonempty rationale
  and UTC timestamp. **The claimed actor kind and reference do not establish authorization
  or whether a person really assessed anything.** Model output remains untrusted.
- `FindingEvidenceLinkRevision`: one immutable `link_id`, consecutive
  `assessment_revision`, exact finding snapshot, deterministic KRN-103 fidelity result,
  assessor proposal and typed expected-value SHA-256 fingerprint. A link cannot be moved
  to another finding revision or source anchor; new/reworded findings require new links
  and complete reassessment. Old contradictory proposals remain in immutable history.
- `InMemoryFindingEvidenceLedger`: tenant-keyed reference; checks registered current finding,
  derives fidelity itself by re-reading the exact trusted source representation, appends
  instead of updating, preserves history, and exposes the newest link assessment per
  statement without hiding older revisions.
- `location_and_fidelity_eligible`: **diagnostic prerequisite only**, true solely if the
  citation resolved and expected quote/value matched the immutable representation. It is
  explicitly **not an authority, sufficiency, support, or promotion decision**.

## Attack/negative acceptance

- Accurate quotation can contradict an explicitly false claim without turning it true.
- A proposed `supports` relation with mismatched/stale/invalid quote is retained as a
  proposal, but does not make locator/fidelity eligibility true.
- Same ID/revision cannot be rewritten, skipped, reattached to another statement or anchor;
  amended finding statement requires a new assessment/link.
- Contradictions and qualifiers remain in history; multiple supports do not vote away conflicts.
- Cross-tenant reads/writes of other tenant links/finding versions fail closed in the reference.
- Model/human-labelled proposals never bestow approval/actor authorization.
- Typed expectation fingerprints distinguish JSON bool, int, string, null and text quote.
- No older v1 API/module contract is changed; no migration, new dependencies or provider code.

## Known limitations and security boundary

This module is **not** an authenticator, authorization layer, verified reviewer register, immutable
durable store, signed audit log, source authenticator, legal fact checker, semantic reasoner,
promotion gate, or policy sufficiency aggregator. Input `tenant_scope` and human actor
references are only trustworthy if a separate application boundary enforces identity and
permissions; Stage 1 tests model namespace isolation but not real RLS. Dataclass equality
and in-memory `RLock` are not tamper resistance. A malicious caller can forge arbitrary
proposal fields and could directly mutate Python reference internals; don't expose these
classes to untrusted clients. Stage 2 owns access control, atomic persistence, audit and
idempotency; KRN-105 owns guarded promotion.

No source text, expected quote or rationale is printed in normal dataclass representations.
Typed expected-value fingerprints are consistency identifiers, not cryptographic secrecy for
low-entropy text; do not expose these fingerprints indiscriminately.
